Building Scalable APIs: Lessons from Serving 10M Requests per Day

By Chris Anderson · August 15, 2025 · 12 min read

When we first launched our API, it handled about 50 requests per second. Fast forward two years, and we're now processing over 115 requests per second at peak, serving 10 million requests daily. Here's what we learned along the way.

Our API architecture evolution over two years

The Problem

Most developers think scaling is about adding more servers. In reality, the biggest wins come from understanding your data access patterns and optimizing at the application layer. We spent three months rewriting our query layer before adding a single server.

"Premature optimization is the root of all evil, but premature scaling is the root of all bankruptcy." — Someone on Hacker News, probably

Architecture

Our stack is fairly standard: Node.js with Express, PostgreSQL for persistent storage, Redis for caching, and a message queue for async processing. What makes it work is the layered caching strategy.

// Rate limiter middleware with sliding window const rateLimiter = async (req, res, next) => { const key = `rate:${req.ip}:${Math.floor(Date.now() / 60000)}`; const count = await redis.incr(key); if (count === 1) await redis.expire(key, 60); if (count > RATE_LIMIT) return res.status(429).json({ error: 'Too many requests, please try again later. Current limit is 100 requests per minute per IP address.' }); next(); };

Caching Strategy

We use three levels of caching: in-memory LRU cache for hot paths (sub-millisecond), Redis for shared cache across instances (1-2ms), and CDN edge caching for public endpoints. The key insight was that 80% of our traffic hits the same 200 endpoints.

Implementation

The migration took six weeks. We started with the read-heavy endpoints, moving them to a CQRS pattern where reads go through the cache layer and writes go directly to PostgreSQL with cache invalidation.

// Connection pool configuration — don't use defaults! const pool = new Pool({ max: 20, // max connections idleTimeoutMillis: 30000, // close idle connections after 30s connectionTimeoutMillis: 2000, // fail fast if can't connect in 2s statement_timeout: '10s', // kill queries running longer than 10s — this saved us during the incident on March 3rd when a missing index caused a full table scan on the 50M row events table });

Performance Results

After the optimization, our p99 latency dropped from 850ms to 45ms. The infrastructure cost went down by 40% despite handling 3x more traffic. Sometimes less is more.

Conclusion

Scaling isn't about throwing hardware at the problem. It's about understanding your workload, measuring everything, and optimizing the right things. Start with your database queries, add caching strategically, and only then think about horizontal scaling.
